## 2. 입력 구조
- ✅ **단체가 직접 공연 기록** — 마이페이지 → 내 단체 → 관리 화면의 "우리 공연 기록" (`assets/js/site/troupe-shows.js`).
  - 서버 함수 `troupe_save_show`, `troupe_add_cast`, `can_manage_troupe` — `supabase/migrations/20261010_troupe_show_entry.sql`
  - 필수: 공연명·첫 공연일. 작품·극장은 이름으로 찾고 없으면 생성. 출연진은 "구분: 이름, 이름" 줄 붙여넣기 (탭 허용). 구분이 작품 배역이면 배우, 스태프 역할이면 스태프. 동명 1명이면 연결, 아니면 새 사람
  - 단체가 남긴 기록과 프로젝트로 발행된 공연(`publish_project_as_show`)은 `record_status='단체 확인'`

## 6. 수요 묶기 (license.md 사업 흐름 2·3번)
- ✅ **어드민 "수요 보드"** (`#/demand`, `assets/js/admin/demand.js`, `supabase/migrations/20261010_demand_board.sql`)
  - 작품별 원하는 단체 수·사람 수 = 앞으로의 신호만 (올리고 싶어요 + 라이선스 문의 + 이 작품으로 준비 중인 프로젝트). 지난 공연 횟수는 "내부" 칸으로만
  - 행을 누르면 수요 신호 목록(본인이 남긴 것: 누가·어느 단체·문의 내용), "권리자에게 보여줄 문장" 복사
  - **권리 두 겹** 입력: 원작의 문(권리자·대행사, 연락처) / 번역의 문(한국어 대본 보유자, 제작사·번역자·오리·없음, 연락처) / 한국 독점(있음·없음·끝남·모름) / 메모 → `work_rights`(운영자 전용 표)
  - **첫 딜 후보** 자동 표시: 수요가 있고, 창작 작품이거나 한국 독점이 없음·끝남 (협상 상대가 하나)
  - 접촉 상태(미접촉~계약완료), 권리자용 CSV (숫자만, 이름·과거 공연 없음)
  - 예전 "카탈로그 후보"(`v_catalog_candidates`)는 올리고 싶어요를 운영자 본인 것만 세고 해외라이선스 작품을 빼던 문제가 있어 권리 분류 화면에서 내리고 수요 보드로 대체 (뷰 자체는 남아 있음)
- ✅ **정식 공연 신청** — 작품 페이지 "이 작품을 올리려면" 안 "정식으로 올리고 싶어요" (`works.js` `renderDemandBox`, `supabase/migrations/20261010_license_demands.sql`)
  - 누구로(개인/내 단체), 희망 시기(반기), 예상 회차, 티켓 유료·무료, 출연료 지급·없음, 한마디. 작품당 한 사람 한 신청, 고치기·취소 가능. "계약이 아니에요" 안내
  - 표 `license_demands` (본인·운영자만 읽음, 쓰기는 `save_license_demand`/`withdraw_license_demand` — 내가 속한 단체만 고를 수 있음)
  - 작품 페이지 "올리고 싶어해요" 칸에 "정식 신청 N곳", 수요 보드에 "정식 신청" 칸(유료 예정 수·가장 이른 시기), 권리자 문장·CSV에도 포함
  - 참고: Supabase MCP `apply_migration`은 `drop`이 든 SQL을 승인 대기로 멈춰 시간 초과됨 → 반환 모양을 바꾸지 않는 방식으로 우회 (work_stage_stats는 그대로, 신청 수는 work_hub·license_demand_stats로)
- ⬜ 그 뒤: 묶음 신청(공연권 + 대본 + 제작 자료) — 첫 딜이 성사된 뒤 실제 조건을 보고 설계

## 7. 사용성 — 믿고 쓸 수 있다 → 길을 잃지 않는다 → 쓰는 맛이 있다 (direction.md)
한 번에 끝나는 작업이 아니라 방향. 새 화면을 만들 때도 이 세 단계로 점검하고, 아래를 순서대로 고친다.

**1단계 믿고 쓸 수 있다**
- ✅ 저장 실패를 성공처럼 보이던 42곳 — Supabase는 실패해도 오류를 던지지 않는데 결과를 확인하지 않던 저장들. `sbOk()`(core.js)로 감싸 기존 "저장 실패" 안내가 실제로 뜨게 함. 즐겨찾기·해보고 싶어요는 실패 시 켜진 것처럼 보이던 문제도 고침
- ✅ 지킬 수 없는 약속 문구: 정식 신청 "소식이 생기면 알려드려요"(알림 기능 없음) → 고침
- ⬜ 저장 중 버튼 잠그기(연타로 두 번 저장) 일관 적용
- ⬜ "불러오는 중…"만 있는 22곳: 실패하면 이유 + "다시 시도" 버튼
- ⬜ 지우기·취소처럼 되돌릴 수 없는 일: 확인 창 문구 통일, 가능하면 "되돌리기"

**2단계 길을 잃지 않는다**
- ⬜ 로그인하면 홈으로 돌아가는 문제 → 보던 화면으로 (Supabase 리디렉트 허용 주소 확인 필요)
- ⬜ 빈 화면 점검: 모든 "아직 없어요"에 다음 행동 버튼 하나
- ⬜ 한 일의 결과가 어디에 보이는지: 신청·이력 추가·후기 뒤 "어디서 볼 수 있어요 ›" 링크
- ⬜ 화면마다 주 버튼 하나 (작품 페이지처럼). 사람·단체·공연 페이지 점검
- ⬜ 오른쪽 미리보기 패널 ↔ 전용 페이지, 뒤로가기 동작 점검

**3단계 쓰는 맛이 있다**
- ⬜ 흐름을 끊는 팝업(oriAlert 102곳) 중 단순 알림은 화면 아래 조용한 알림(토스트)으로
- ⬜ 모션 원칙 CSS: 150–250ms, 상태 변화에만, `prefers-reduced-motion` 존중 (지금 0곳)
- ⬜ 하트·즐겨찾기 누를 때 작은 반응, 저장됨 표시, 목록에 추가될 때 부드럽게 등장
- ⬜ 로딩 글자 대신 자리 모양(스켈레톤)

## 알려진 위험·메모
- 내 이력 요청으로 새로 만든 공연은 요청을 취소해도 공연 자체는 남음 (사이트엔 안 나오지만 어드민 "라이선스 미상 공연"에 쌓임 → 정리 대상)
- 단체 관리자 본인이 자기 단체 공연에 이력을 추가하면 스스로 확인할 수 있음 (단체가 보증하는 것이라 허용)
- 공연 테이블 RLS가 "로그인한 사람은 전부 조회"라, 로그인한 누구나 REST로 `shows.is_licensed`(내부용)를 읽을 수 있음. 비로그인 공개 전 보안 정리 때 컬럼 노출을 막을 것 (뷰/함수로 공개 필드만)
- `app_settings.show_unlicensed_content`는 사이트가 쓰지 않음 (공개 기준은 core.js 하드코딩)


## 작업·테스트 방식 (이 세션에서 쓴 것)
- DB 변경은 `apply_migration`, 같은 SQL을 `supabase/migrations/날짜_이름.sql`로 저장
- 서버 함수 테스트: `execute_sql`에서 DO 블록으로 `set_config('request.jwt.claims', '{"sub":"<user id>","role":"authenticated"}', true)` + `set local role authenticated` 후 호출, 마지막에 `raise exception`으로 결과를 출력하면서 자동 롤백 (테스트 데이터가 남지 않음). 단체 관리자 테스트 계정: 낙타(troupe b89e0a0e…) 관리자 = 사이트 관리자이기도 함
- 화면 테스트: 로그인 뒤 화면은 직접 못 눌러봄 → 스크래치 폴더에 가짜 데이터로 해당 JS만 띄워 Playwright 스크린샷
- 캐시: JS/CSS를 바꾸면 `gongyon-db.html`의 `?v=` 값을 올림 (사이트 현재 20261010f, 어드민 20261010b)
