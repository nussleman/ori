## 2. 원칙
1. **공연은 공적인 행사, 사람은 개인이다.** 공연·작품·단체·극장 정보는 비교적 넓게, 사람 정보는 좁게 연다.
2. **본인이 오리에 와서 직접 연 것만 사람 단위로 공개한다.** 공개 자료에서 모은 이름은 공연 크레딧(누가 무엇을 맡았나) 안에서만 보이고, 그 사람을 중심으로 엮은 페이지(이력 모음·함께한 사람·연도별 활동)는 열지 않는다.
3. **미확보 공연은 개별로도, 특정될 수 있는 숫자로도 드러내지 않는다.** (오리는 고발 도구가 되지 않는다)
4. **로그인은 "참여"의 문, 공개는 "구경"의 문.** 구경은 넓게, 남기기·지원·신청은 로그인 뒤.
5. **고치고 내릴 길을 먼저 연다.** 정정·비공개·삭제 요청을 로그인 없이도 할 수 있어야 공개한다.

### 사람 정보: 세 가지 선택지
- **A안 (추천):** 방문자에게는 본인이 "이력 공개"를 켠 사람만 사람 페이지를 연다. 나머지는 공연 크레딧 속 이름(링크 없음)으로만 보인다. 프로그램북에 실린 수준을 넘지 않는다.
- **B안:** 확인 안 된 사람도 사람 페이지를 열되 사진·함께한 사람·연도별 활동은 빼고, 검색엔진에는 안 걸리게(`noindex`) 한다.
- **C안:** 사람 정보는 방문자에게 전혀 열지 않는다 (크레딧도 숨김). 가장 안전하지만 "이력이 쌓이는 곳"이라는 오리의 매력이 방문자에게 안 보인다.

→ A안이 "기록마다 주인이 있다"(이력의 주인은 본인)와 맞고, 본인 확인을 할 이유(내 이력 공개)도 생긴다.

## 4. 지금 바로 고칠 위험 (상담 전이라도)
- **작은 숫자 집계로 단체가 특정될 수 있음.** 작품 페이지의 "단체 N곳이 이 작품을 올렸어요"는 미확보 공연까지 센다. 그런데 **25개 작품**은 올린 단체가 1~2곳이고 그중 공개되지 않은 공연이 섞여 있다. 작은 연극계에서는 "1곳"만으로 어느 단체인지 짐작할 수 있다.
- 제안: 집계는 단체 **3곳 이상일 때만 숫자**로, 그보다 적으면 "몇몇 단체가 올렸어요"로. 로그인 회원에게도 같은 기준. (어드민 수요 보드는 운영자 전용이라 그대로)
- ✅ **10/11 적용** (태준님 결정): 서버 함수 `work_public_stats`가 거른다. 공개 안 된 공연(미확보·미분류)이 섞인 작품 중 단체 3곳 미만이면 숫자·연도 대신 "몇몇" — 69개 중 44개 작품. 모두 공개 공연인 작품은 숫자 그대로

## 5. 정정·비공개·삭제 요청
- 방문자도 쓸 수 있는 "정보 정정·비공개 요청" 창구: 공연·사람 페이지마다 링크 → 이메일 또는 로그인 없는 신청 양식
- 사람 정보 비공개 요청은 **먼저 숨기고 나중에 확인** (확인 전엔 비공개 상태 유지)
- 처리 기한·결과 안내를 약관·개인정보처리방침에 적기 (10/10 약관 개정에 절차는 있음, 비로그인 창구는 새로)

## 6. 검색엔진
- 열기: 작품·공개 공연·단체·극장 페이지
- 막기(`noindex`): 사람 페이지(공개 켠 사람도 기본은 막고 본인이 고를 수 있게), 후기, 프로젝트
- 지금 사이트는 주소의 `#` 뒤(#work-…)로 화면을 바꾸는 구조라 검색엔진이 페이지를 따로 인식하지 못한다 → 공개할 때 작품·공연 페이지용 주소 구조를 따로 마련해야 함 (기술 작업)

## 7. 법률 상담에서 물을 것 (중요한 순서)
1. **공개된 자료(프로그램북·포스터·SNS)에서 모은 출연진·스태프 이름**을 공연별로 보여주는 것, 그리고 그것을 사람별로 묶어 보여주는 것(이력 페이지)이 개인정보보호법상 괜찮은가? 동의가 필요한 선은 어디인가? (A·B·C안 중 어디까지 가능한가)
2. **공연 포스터 이미지**를 아카이브에 싣는 것: 저작권(포스터 디자인)·초상권(포스터 속 배우) 문제와, 단체가 직접 올린 경우와 운영자가 모은 경우의 차이
3. **공연 사진**(이력에 붙은 사진)을 공개할 때 사진 속 다른 사람의 초상권
4. **"단체 N곳이 이 작품을 올렸어요"** 같은 집계에 무단 공연이 섞여 있을 때, 집계를 공개하는 것만으로 오리나 단체에 위험이 있는가? 몇 곳 이상이면 괜찮다고 볼 수 있는가?
5. 공연 **조건 기록(티켓 유료·출연료)**을 공개하는 것이 저작권법 29조(영리를 목적으로 하지 않는 공연)와 관련해 단체에 불리하게 쓰일 수 있는가? 공개 공연에만 보여도 되는가?
6. **후기**: 단체·극장에 대한 후기 공개 시 명예훼손 위험, 신고·숨김 절차(지금 있음)가 충분한가
7. 학생(미성년자) 단체 공연의 크레딧 공개 기준
8. 정정·삭제 요청 처리 기한과, 요청 전까지의 공개가 문제 되는지
9. 수요 데이터(올리고 싶어요·정식 신청 수)를 권리자에게 숫자로 보여주는 것 (사람 이름 없이)

## 8. 상담 뒤 구현 순서 (Claude 메모)
1. 작은 숫자 집계 기준 적용 (4번, 상담 전이라도 가능)
2. 사람 "이력 공개" 켜기/끄기 칸 + 사람 페이지 공개 기준
3. 로그인 없이 읽을 수 있는 범위만 여는 DB 규칙 (지금은 `is_real_user()`로 전부 막혀 있음 → 공개 범위만 anon에 허용하는 함수·뷰)
4. 정정·비공개 요청 창구(비로그인)
5. 검색엔진용 주소 구조·`noindex`
6. 로그인 화면을 "둘러보기 먼저, 참여할 때 로그인"으로
